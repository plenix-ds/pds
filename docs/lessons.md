# Lessons

What the 0.x project taught us (plan §2), plus confirmed lessons added after each M/L item. Keep each lesson to one line: what happened, then the rule.

## From 0.x (2026-10-08 to 2026-11-03)

- **241 versions in 26 days, with the DataGrid reversed 5 times.** → Decide before building: a written spec and `DESIGN.md` come first. Rulings go in the ledger, not silently into code.
- **CI had 0 green runs out of 1,509, and checks weren't a merge gate.** → Required checks only, and diff-aware so only new problems block. Tests are quarantined with an owner within 24h, never deleted.
- **0 of 58 Codex PRs were merged.** → One team and one instruction source (Rulesync). Codex stays on standby.
- **The owner was the gate on every merge and look: 341 queued questions, 19–21 stuck merges.** → Full autonomy, decision cards with the recommendation applied, and never asking twice (`decisions.yaml`).
- **About 35% of effort went to process and 25% to rework.** → Small PRs the same day. Measure with the checks, not with reports.
- **About 56 agent processes ran on 15 GB, near out-of-memory.** → Limits come from `agents.config.yaml`, with a memory limit per session.
- **One shared owner GitHub identity made 715 of 786 commits.** → Bot identity per role through the GitHub App, and signed comments until then.
- **Cron polling every 1–2 minutes.** → Webhooks.
- **An agent's report was taken as fact.** → Evidence (Ran/Skipped/Planned/Manual) plus `git log` and the checks.
- **`check | tee log` hid failures** (from CTM). → Workflows use `bash` with `pipefail`.
- **"Arabic never shipped" was wrong:** a stale local clone was read instead of `main`. → Check `origin/main` before claiming anything about the repo.

## PDS 1.0

- **CTM 3.0 re-asked the owner after each answer (new cards D-0032, D-0033) and ran each answer as its own long chain.** → The owner's answer is final: act on the sensible reading, say it in one line, handle all answers in one pass, and refresh the dashboard once (D-0035).
- **PDS had no dashboard page when the owner asked for "the html page like CTM".** → When the owner points at a working example, ship that example first, then improve it (D-0034).

## From PDS 1.0 (2026-11-05)

- **Twice, changelog fragments merged in the same merge-queue group as the version PR shipped without CHANGELOG lines** (0.87.0: #311; 0.88.0: #334, #292). → At a release, check `changelog.d` at the exact release commit; put any late fragment in the GitHub release notes and fold it on `main` right after.
- **A required check was blocked by its own cancelled run** (#345): opening a PR with a label fires two events, and `cancel-in-progress` cancelled one. → Required checks never use `cancel-in-progress`; a run that takes seconds just finishes.
- **Four duplicate builds in one day** (#324/#320, #364/#365, #417/#420, #422/#425): two engineers built the same issue because a hand-off said "the other engineer if free" and nobody had claimed it first, so one finished PR was thrown away each time. → Before building, comment "claiming" on the issue and check for an open PR that mentions it; the first claim wins, and the Delivery Lead closes the later PR as a duplicate.
- **A queued PR's branch is locked** (#306): pushing to it fails until it is dequeued (`dequeuePullRequest`), and a comment saying "pushed" before checking the push result was wrong. → Check the push result before reporting it; dequeue first, push, then re-queue.
- **A PR merged with an open G3 point although `g3-changes-requested` was on it** (#471): it entered the merge queue at 01:06, the label came at 01:08, and the queue's check had already run. → When adding `g2-changes-requested` or `g3-changes-requested`, look at the merge queue first and dequeue the PR if it is there (D-0056, D-0062).
- **The tag workflow was red on 0.89.0 and 0.90.0** (#724): the GitHub release was made by hand while the tag job waited in the queue, and the job stopped at "already has a GitHub release". → The tag job keeps whatever is already published, publishes only what is missing and ends with the G8 version check; don't create the release by hand, let the tag job do it.
- **A release smoke test probed `/api/v1/` on the public URL and got Authentik's 302** (0.90.0): only `/cdn/` is public. → Check the API through nginx on the web host (`curl -H "Host: design-system.lighthouseway.org" http://127.0.0.1/api/v1/index.json`), as the 0.89.0 smoke test did; a 302 is not a failed release.
- **It happened again on 0.91.0, 0.92.0 and 0.93.0 (#842, #872, #882): a fragment merged in the queue just before the release commit, so its code shipped without its line.** Checking `changelog.d` by hand when the PR is cut can't catch a merge that happens later in the queue. → After the release commit lands, read `changelog.d` *at that commit*. Fold any fragment into the released section in a follow-up PR, and include it in the GitHub release notes. CI now fails a version PR, in its merge group, while `changelog.d` holds a fragment (`tools/ci/check-release-notes.mjs`, #884).

## Seeded from template v2.4, Appendix A (D-0084)

Lessons A-01 to A-05, A-10 to A-13 are already above in other words; these are the ones not yet recorded.

- **A late, large merge silently dropped controls (A-06).** → Integrate small and often; before resolving a shared file, list what each side added and confirm both survived.
- **Owner choices were never written down, so layouts and icons flip-flopped (A-07).** → Every choice is a decision with an enforcing check; an unrecorded reversal fails G5b.
- **`main` had no branch protection and stayed red for weeks (A-08).** → Required checks on `main` from day one; a red `main` is an S1 bug.
- **Two agent teams worked with different rules (A-09).** → One team, one rulebook; GitHub is the only channel.
- **Test fixtures were hand-trimmed and hid missing fields (A-14).** → Fixtures come from, or are checked against, the contract files.
- **A dependency upgrade removed a file that string-only tests missed (A-15).** → Upgrades fetch every referenced file before merging.
- **The config said 8 slots while the plan and the instruction file said 4 (A-16).** → Settings live only in the registry (`agents.config.yaml`); documents link to it by setting name, never repeat the number (check 15). This plan now does that.
- **A label, a tag or a card move made by an agent started no workflow, so the next role never woke (A-17).** → Events caused by `GITHUB_TOKEN` start no workflows (except `workflow_dispatch` and `repository_dispatch`). Hand-offs use the GitHub App token or an explicit dispatch (check 16, #772).
- **The dispatcher heartbeat went stale 28 minutes after it was built (#821, 2026-11-06).** The timers run `team.sh` from the Delivery Lead's checkout of main; #772 (with the heartbeat) merged at 22:06, but that checkout was not pulled until 22:24, so the nudge kept running the old script and wrote no heartbeat. → A merged change to the scripts must reach the host on its own: `team.sh nudge` fast-forwards its checkout each round when it is on a clean `main` (`selfupdate`). The daily watchdog is the check that caught it. Long-running services (`pds1-pickup`) still need a restart to load new code.
- **The team slept 10 hours with an S1 open (#895, 2026-11-07).** The nudge called a round quiet when nothing on GitHub had changed and no PR was open; idle agents change nothing, so from 04:47 to 15:17 every round was quiet while #893 (S1) waited, and pickup drops events older than 30 minutes, so nothing retried. → A round is quiet only when no role has open, unblocked, non-`later` work as well (`deploy/agents/dispatch.mjs`); an S1/S2 is named to its role every round until the role answers; the heartbeat shows the unanswered count and the hourly watchdog opens a P0 when it stays above 0 for 2 rounds (`tools/ci/dispatch.test.mjs`).
- **0.91.0 to 0.93.0 broke RedSave's typecheck twice over (#893, #894).** The move to tsc-generated declarations dropped three published type names, and the self-hosting archive shipped a `plenix.d.ts` that imported 317 files from a `types/` folder it did not hold. The consumer type test had silently stopped checking (its fixture pointed at an old build path), so neither showed. → A published type name never goes (`tools/checks/published-names.mjs`, from each release's recorded names). Every relative import in a declaration file resolves inside the artifact that ships it (`tools/publish/dts-closure.cjs`, run by the build and the release dry run). A test that reads a build output fails when that output is missing; it never passes on nothing.
- **Every PR that recorded a decision conflicted in the merge queue (#955, 2026-11-07).** One shared `decisions.yaml` (and one ADR index table) meant any two queued PRs touched the same lines; the DS Architect rebased one PR five times in a day, and the same decision ID was taken twice (D-0101, D-0102). → One file per decision in `decisions.d/`, the ADR index generated from the ADR files, ids from `node tools/decision-id.mjs`, and a check that fails on an id already on main. The same pattern as `changelog.d/`: a shared append-only file is a conflict magnet, so each entry gets its own file.
- **A PR merged with a recorded G3 FAIL (#1060, #1068, 2026-11-08).** Auto-merge was switched off for a release hold; the reviewer then posted `G3: FAIL` as a comment without the `g3-changes-requested` label (a comment stops nothing, since every agent shares one GitHub account); the Delivery Lead re-armed the PR when the hold lifted without re-reading its comments, and it merged. → Two rules: a reviewer adds the gate label with every FAIL and removes it with the PASS; whoever re-arms a held PR first reads its comments and reviews for a gate FAIL newer than its last commit. A workflow that sets the label from the FAIL comment is the safety net (issue linked on #1068).
- **A build is not a render (#1034, #909, 2026-11-08/09).** 93 story files used JSX without `import React`; they built, and they threw "React is not defined" in the browser, rendering nothing. The story axe runner waited for `#storybook-docs`, which the empty page satisfied, so about 250 stories passed axe vacuously, and the story PRs' "axe: no findings" lines were wrong. It surfaced only when the job was sharded and began reporting "the story threw while rendering". 78 real accessibility findings had been invisible. → Proof for anything shown in a browser is a render in a browser, not a build: a runner must wait for a rendered root and fail on an empty one, and a first run that reports zero findings over a new corpus is a reason to check that the corpus rendered.
- **A session that died looks like a slow one (2026-11-08).** The QA Engineer session was killed by the OOM killer twice (2.5 GB limit, headless Chrome) and stood in tmux as "stopped"; PR #1105 sat red for two hours with comments no one read, and a mention does not restart a dead session. → When a role is slow, check its activity record and its tmux pane before commenting again; give a role that runs a browser its own memory limit (`memory_limit_gb` in `agents.config.yaml`).
- **"Released" was read as "done" (2026-11-08/09).** PDS reported 1.2.0 and 1.3.0 as live and "CTM runs it" (its `version.json`), but CTM had not switched its screens to the new parts. The read-only tiles and LoadingState were unused, and CTM's own D-0045 had replaced the owner's 1366 frame (D-0093) with the full window. The owner saw none of what he had approved. → A report to the owner says what he will see: "live in Plenix", "CTM loads it" and "CTM uses it on its screens" are three separate facts, checked separately (grep the consumer for the new prop, look at the live page). A consumer decision that contradicts an owner decision is raised the same day (CTM#289).
- **Three releases in a row stopped or raised a bundle limit at the deploy (1.3.0 #1103, 1.4.0 D-0142, 1.5.0 D-0144; #1144).** The one-part budgets ran only in `deploy.sh` and the release dry run, so PRs that each fit merged green and went over together; the size decision was then made under release pressure. → The CI job "Bundle budgets" runs `tools/agent/one-part-sizes.js --check` on every PR that touches the package's sources or build, and in the merge group, where queued PRs meet. Over a limit, the PR loads the new code on first use or carries a decision record with G3.
- **The nudge skipped every idle session for 10.5 hours and logged nothing (#1166, 2026-11-10).** `team.sh wake` decides a session is idle only when its input box is empty, and it read the *first* `❯` line of the last 12 screen lines. A session that had run `/remote-control` (every session did at 00:52, when they were renamed) kept the line `❯ /remote-control PDS1 · …` above its real box; an idle pane never scrolls, so that history line stayed in view, the box looked full, and `wake` returned "not idle" for every such session, with no log line. Only sessions that kept producing output (the Product Lead) were ever nudged. The Component Engineers sat idle with #1152 and #1155 Ready; the Product Lead found it by hand. → The input box is the last `❯` line, never the first. `tools/ci/wake.test.mjs` runs `wake` against pane fixtures (stub tmux), including this one, and fails on the old logic. A refusal to wake a session that has work is now logged with its reason (`nudge: <role> not woken: …`; "working" stays quiet), so a guard that misreads a pane shows up in `team.log` instead of as silence. Judging "idle" from screen text is fragile; test it against real captured panes.
- **A stopped role named with Ready work was never started; the webhook forwarder had been in a restart loop for 50 minutes (#1182, 2026-11-10).** `gh webhook forward` creates a repository hook while it runs and deletes it on a clean exit. At 15:00 UTC its connection dropped and it exited without deleting the hook, so every restart (systemd, every 30 s) failed with "Hook already exists": 99 failures, no webhook reaching pickup, and nothing said so. The fallback, the repository event feed, is lossy and hours late (the 15:27 mention of the Release Architect never appeared in it; other events arrive 2 h late and are dropped as stale), and the scheduler starts a role only for a labelled issue or a held event, so a comment mention of a stopped role whose label had been removed (#1163 handed to the PM at 14:41) reached nobody. → `deploy/agents/webhook-clean.sh` runs before every forwarder start and deletes the forwarder's own leftover hook (`tools/ci/webhook-clean.test.mjs`); the nudge heartbeat shows `webhook: <state>` and logs every round the forwarder is not active. A fallback that is lossy is not a fallback: watch the fast path, and when handing an item to a role, label it for that role (the label is what the scheduler reads), not only a comment.
